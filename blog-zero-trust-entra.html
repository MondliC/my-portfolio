Zero Trust Architecture with Microsoft Entra at the Core — My Notes

What I took from the article, how it connects to cloud security operations, and what I want to validate in my hybrid identity lab.

Mondli Nkosi 27 Sep 2026 Original article ↗

Why this article caught my attention

What stood out to me is the idea that Zero Trust is not a product that you simply enable. It is an operating model built around continuously evaluating whether access should be allowed.

In a Microsoft environment, Entra ID becomes extremely important because it can sit at the centre of many access decisions across Microsoft 365, Azure, SaaS applications and hybrid environments.

“You are inside the network, therefore I trust you” becomes “Prove who you are, prove the device is trustworthy, evaluate the risk, and only then decide what access you should receive.”

The Zero Trust loop

The three principles I associate most strongly with Zero Trust are verify explicitly, use least privilege and assume breach.

Verify explicitly: authentication alone is not enough. Access decisions should consider identity, device state, location, application, authentication method, risk signals and session context.

Use least privilege: users and administrators should receive only the access they need, for only as long as they need it.

Assume breach: security architecture should be designed under the assumption that credentials, sessions or endpoints may eventually be compromised.

The third principle changes how I think about detections and access controls. Instead of asking only whether an attacker can get in, I also want to know: if this identity is compromised, how far can the attacker move?

Entra ID as the control plane

One of my main takeaways is that Entra can effectively become the identity control plane for Zero Trust. Conditional Access is where much of this becomes practical.

  • User and group membership
  • Sign-in risk
  • Device compliance
  • Authentication strength
  • Application being accessed
  • Network or location signals
  • Session conditions

The result can then be to allow access, require MFA, require a compliant device, require stronger authentication, apply session restrictions or block access entirely. Identity effectively becomes part of the security perimeter.

Privileged access deserves different treatment

Administrator access should not behave like normal user access because privileged identities have a much larger blast radius if compromised.

  • Dedicated administrative accounts
  • Phishing-resistant authentication
  • Privileged Identity Management
  • Just-in-time elevation
  • Time-limited privileges
  • Strong device requirements
  • Better monitoring and alerting

This connects directly with what I have been learning around Entra roles and Azure RBAC. A user having permanent privileged access creates an attack path even when that privilege is not being actively used.

PIM helps change the model from “this person is always an administrator” to “this person is eligible to become an administrator when there is a legitimate reason.”

Zero Trust in a hybrid environment

This part is especially relevant to the hybrid identity lab I am building. Moving to Entra does not automatically make Active Directory disappear.

Organizations can still depend on Kerberos, NTLM, domain controllers, Group Policy, legacy applications, AD security groups, and domain or forest trusts.

An attacker compromising an on-prem identity may still find a route into cloud resources if that identity is synchronized into Entra ID. Likewise, excessive cloud permissions can create attack paths that eventually impact hybrid infrastructure.

For me, this reinforces why hybrid identity security needs visibility across both sides:

Active Directory activity → Entra authentication → cloud privilege → application/resource access

This is also where Defender for Identity, Defender XDR and Sentinel become useful together.

MFA does not equal Zero Trust

One misconception I want to avoid is treating MFA as the end goal. MFA is only one control and does not automatically protect against stolen session tokens, excessive permissions, compromised endpoints, OAuth abuse, standing privilege or poor guest lifecycle management.

This is especially important when looking at token theft. If an attacker steals an authenticated session, they may not need to perform MFA again.

Conditional Access should be treated carefully

A practical operational lesson is to use report-only mode before enforcing Conditional Access policies. A badly designed policy can easily lock out administrators or legitimate users.

Design → Report-only → Observe → Pilot → Tune → Enforce

I would also make sure break-glass accounts are considered before enforcing large Conditional Access changes.

Detection opportunities

Risky authentication

Look for users with increasing sign-in risk or unusual authentication behaviour using sources such as SigninLogs, AADUserRiskEvents and AADRiskyUsers.

Privileged role activity

I would investigate Global Administrator activation, Privileged Role Administrator activity, role assignments outside normal patterns, repeated PIM activations and newly eligible privileged users.

Conditional Access failures

Repeated failures can reveal attacker behaviour, for example compromised credentials followed by a device-based block and then repeated access attempts from different locations or sessions.

Workload identities

Service principals and managed identities should also be treated as identities. I would monitor new credentials added to applications, new service principals, unexpected consent, unusual workload authentication and high-risk permissions granted to applications.

How I would test this in my lab

Test 1 — Conditional Access enforcement

Create a policy requiring MFA or stronger authentication for privileged accounts, then compare successful authentication, Conditional Access failure, authentication requirements and the resulting Sentinel telemetry.

Test 2 — Privileged Identity Management

Replace permanent privileged access with an eligible role and monitor role activation, expiration, audit events and corresponding Sentinel logs.

Test 3 — Risk-based access

Generate suspicious sign-in behaviour in a controlled environment and investigate whether risk signals influence Conditional Access decisions.

Test 4 — Hybrid identity correlation

Generate authentication activity against the on-prem domain controller and then use the same synchronized identity against Entra resources.

Windows Security Events → Defender for Identity → Entra Sign-in Logs → Defender XDR → Sentinel

My biggest takeaway

The main lesson I took from this article is that identity has effectively become one of the most important security control points in modern environments.

Zero Trust is not simply MFA, Conditional Access or Defender. It is the combination of identity, device trust, least privilege, risk signals, policy, telemetry and continuous validation.

For someone working in cloud security, understanding Entra is therefore not only an IAM skill. It is increasingly a detection, incident-response and attack-path skill as well.

Question I want to explore next

If a synchronized hybrid identity is compromised on-prem, what controls and telemetry can stop or detect the attacker before they successfully pivot into Entra ID and Azure resources?

That is something I want to test practically in my hybrid identity lab.
