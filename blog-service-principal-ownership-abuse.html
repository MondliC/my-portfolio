Service Principal Ownership Abuse in Entra ID — My Notes

What I learned from a Semperis EntraGoat scenario showing how ownership of a privileged service principal can turn a low-privileged compromise into a much more serious identity attack path.

Mondli Nkosi 28 Sep 2026 Original article ↗

Why this scenario caught my attention

I have been spending more time looking at attack paths in Microsoft Entra ID, especially relationships that are easy to miss when we focus only on users, groups and traditional administrator roles.

This Semperis EntraGoat scenario stood out because it shows how a configuration that looks legitimate on its own can become a privilege-escalation path when ownership and application privilege are combined.

The scenario starts with a compromised low-privileged user. The important detail is what that user owns: a service principal with meaningful privilege.

The attack path

The attack can be simplified to:

Compromised user → Owned service principal → Add application credential → Authenticate as service principal → Abuse privileged role → Compromise a privileged account

The attacker does not necessarily need to compromise another user password. Instead, they pivot from a human identity into a workload identity.

Why service principal ownership matters

A service principal is the security identity an application uses inside an Entra tenant. It can hold permissions, directory roles and credentials of its own.

Ownership is a legitimate administrative feature. Developers and application teams often need to manage applications without involving a tenant administrator for every change.

The risk appears when a low-privileged user owns a service principal that has powerful permissions or roles.

Standard user → owns → Service principal → assigned → Privileged Entra capability

Looking only at the user may not reveal anything unusual. Looking at the relationship graph tells a different story.

The move from user identity to workload identity

One of the most useful lessons from the scenario is the distinction between delegated user access and app-only access.

A normal interactive user session can be evaluated using controls such as MFA, Conditional Access and user risk. A service principal can authenticate using application credentials such as a certificate or client secret and operate using its own identity.

Attacker → Compromised user → Owned service principal → Application credentials → Privileged workload identity

This matters because workload identities do not behave like normal users, and user-centric protections do not automatically remove the risk.

The defender lesson: privilege is a graph

My biggest takeaway is that privilege should not be evaluated one identity at a time.

A standard user may have no administrator role and still participate in a path that eventually reaches privileged access.

Relationships worth assessing include:

  • Service principal ownership
  • Application ownership
  • Group ownership and membership
  • Directory role assignment
  • Microsoft Graph application permissions
  • Azure RBAC assignments
  • PIM eligibility

Individually, some of these can look harmless. Combined, they can form an attack path.

What I would hunt for

1. Users who own privileged service principals

Regular users owning applications should not automatically be treated as malicious. The useful question is whether a low-privileged user owns an application identity that has dangerous permissions or roles.

2. New credentials added to applications

Adding a client secret or certificate changes who can authenticate as an application. I would investigate unexpected credential additions, especially when the target service principal is privileged.

3. Privileged workload identities

I would want an inventory that ties together owners, credentials, Microsoft Graph permissions, directory roles and recent authentication activity for service principals.

4. Ownership changes

Ownership changes around privileged applications are security-relevant. I would ask who added the owner, whether the relationship was expected, and whether credential creation or application authentication followed shortly afterwards.

Detection hypothesis

If a low-privileged identity owns a privileged service principal and then modifies its credentials, that combination could indicate an attempt to pivot from a user identity into a more privileged workload identity.

The interesting detection opportunity is therefore not necessarily one event. It is the sequence:

User → owns → Privileged service principal → Credential added → Service principal authenticates → Privileged directory operation

That turns individual audit records into an attack story.

How this fits into my Entra ID lab

This scenario fits directly into the Entra attack-path work I am already doing with ROADrecon, AzureHound, BloodHound CE, Microsoft Sentinel and Defender XDR.

The question I want to move toward is not simply:

Which users are administrators?

It is:

Which relationships could eventually allow an identity to reach administrative privilege?

A lab scenario could deliberately create:

LAB-USER → owns → LAB-ANALYTICS-SP → privileged relationship → Sensitive Entra capability

Then I can assess how the relationship appears across the graphing tools and what telemetry is produced when the path is abused in a controlled way.

Purple-team workflow I want to test

Build the misconfiguration → Enumerate the relationship → Identify the attack path → Simulate controlled abuse → Collect telemetry → Hunt in Sentinel / Defender XDR → Create detection logic → Remediate → Retest

The goal is not only to prove the attack works. The more useful question is whether the security team would detect the sequence early enough to stop it.

Remediation considerations

  • Regularly review service principal ownership.
  • Remove unnecessary owners.
  • Review privileged directory roles assigned to service principals.
  • Audit high-risk Microsoft Graph application permissions.
  • Monitor application credential creation.
  • Remove stale secrets and certificates.
  • Decommission unused applications.
  • Improve governance around workload identities.
  • Investigate unusual app-only authentication activity.

My biggest takeaway

Ownership is part of privilege.

An identity does not need to directly hold an administrator role to be dangerous. Sometimes the real risk exists several relationships away.

User → Ownership → Application → Credential control → Privileged identity → Tenant impact

Attack-path analysis forces us to look at identity as a graph instead of a flat list of roles and permissions.

For defenders working with Entra ID, that mindset is increasingly important as environments accumulate more applications, automation identities, service principals and hybrid identity relationships.

Question I want to explore next

Can I detect the transition from a compromised human identity to a privileged workload identity before the attacker performs the final privileged action?

That is the part I want to test practically in my lab.
